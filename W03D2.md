## 2. The row's new shape — what and why (~15 min)

Right now a click on `.delete` fires instantly. To swipe, you need two layers per row:
a bottom layer that's always there (the red Delete button), and a top layer that
slides to reveal it (the checkbox, text — everything currently visible).

In `render()`, restructure the row. Currently you build `li` and append
`checkWrap, span, del` directly to it. Change it to build two containers first:

```js
const actions = document.createElement("div");
actions.className = "row-actions";
actions.appendChild(del);

const content = document.createElement("div");
content.className = "row-content";
content.append(checkWrap, span);

li.append(actions, content);
```

(`del` and `checkWrap` and `span` are the same elements you were already building —
just gather them into these two wrapper `<div>`s instead of appending straight to
`li`.)

- `row-actions` — sits underneath, holds the Delete button, red background.
- `row-content` — sits on top, holds everything the user normally sees. This is the
  layer that slides.

## 3. Style the two layers (~20 min)

```css
#list li {
  padding: 0;   /* the content div handles its own padding now */
}

.row-actions {
  position: absolute;
  inset: 0;
  display: flex;
  justify-content: flex-end;
}

.row-actions .delete {
  background: #ff3b30;
  color: white;
  border: none;
  font: inherit;
  padding: 0 1.25rem;
}

.row-content {
  display: flex;
  align-items: center;
  gap: 0.75rem;
  padding: 0.75rem 1rem;
  background: white;
  transform: translateX(0);
  transition: transform 0.2s ease;
  touch-action: pan-y;
}
```

- `.row-actions { position: absolute; inset: 0 }` — fills the whole row, sitting
  behind `.row-content` (later elements paint on top of earlier ones by default, so
  `row-content` naturally covers it).
- `justify-content: flex-end` — the Delete button sits at the right edge; sliding
  `.row-content` left reveals it from under the right side, exactly like Reminders.
- `transform: translateX(0)` + `transition: transform 0.2s ease` — the resting
  position, and a smooth animation *when the value changes*. You'll set this value
  directly with JavaScript on every pointer move — and that's where the transition
  becomes a problem, next step.
- `touch-action: pan-y` — tells the browser "let the user scroll the page vertically
  by touch here; I'm handling horizontal drags myself." Without it, your horizontal
  swipe would fight the browser's own touch-scroll handling on a phone.

Reload. You'll see the Delete button peek out if you inspect with DevTools and
manually nudge `transform` — but there's no drag yet.

## 4. Pointer Events — what and why (~15 min)

Before touch and pointer events, you'd have written separate handlers for mouse
(`mousedown`/`mousemove`/`mouseup`) and touch (`touchstart`/`touchmove`/`touchend`) to
support both a trackpad and a phone. **Pointer Events** unify them: `pointerdown`,
`pointermove`, `pointerup` fire the same way whether the input is a mouse, a finger,
or a pen.

The other piece you need is `setPointerCapture(pointerId)`. Once called on an
element, that element keeps receiving `pointermove` and `pointerup` events for that
specific pointer **even if it leaves the element's boundaries** — which it will, the
moment you start dragging. Without it, dragging fast would "lose" the element and
your moves would stop firing.

Read `sidelines/pointer-events.md` now if any of this feels shaky.

## 5. Write the drag handlers — type it (~30 min)

In `app.js`, add (near your other `list.addEventListener` calls):

```js
const OPEN_X = -88;
let drag = null;

list.addEventListener("pointerdown", (event) => {
  const content = event.target.closest(".row-content");
  if (!content) return;

  drag = { content, startX: event.clientX, currentX: 0 };
  content.style.transition = "none";
  content.setPointerCapture(event.pointerId);
});

list.addEventListener("pointermove", (event) => {
  if (!drag) return;

  const delta = event.clientX - drag.startX;
  drag.currentX = Math.min(0, Math.max(OPEN_X, delta));
  drag.content.style.transform = `translateX(${drag.currentX}px)`;
});

list.addEventListener("pointerup", (event) => {
  if (!drag) return;

  drag.content.style.transition = "";
  const open = drag.currentX < OPEN_X / 2;
  drag.content.style.transform = `translateX(${open ? OPEN_X : 0}px)`;
  drag = null;
});
```

Line by line:

- `OPEN_X = -88` — how far left the content slides when fully "open" (negative = left,
  roughly the Delete button's width).
- `content.style.transition = "none"` on `pointerdown` — **this matters.** The CSS
  transition you set is meant for the snap animations at the *end* of a drag. If it
  stayed on *during* the drag, every `pointermove` would fight the previous
  transition, and dragging would feel laggy and delayed instead of following your
  finger exactly. Turning it off during the drag, then back on (`= ""`, meaning "use
  the CSS rule again") on release, gives you: instant tracking while dragging, smooth
  animation when you let go.
- `content.setPointerCapture(event.pointerId)` — as explained above: keeps the moves
  coming to `content` for this specific pointer, no matter where it wanders.
- `Math.min(0, Math.max(OPEN_X, delta))` — clamp the drag distance so it can't go
  past fully-open (`OPEN_X`) or past the resting position (`0`) in the other
  direction.
- On `pointerup`: `open = drag.currentX < OPEN_X / 2` — "did the drag pass the
  halfway point?" If yes, snap fully open; if no, snap back to `0`.

Save, reload, add a couple of tasks. Click-and-drag a row's content left with your
mouse. It should follow your cursor, then snap open or closed depending on how far you
dragged.

## 6. Wire the revealed Delete button, and keyboard access (~10 min)

The `.delete` button already exists inside `.row-actions` and your existing click
listener already handles `button.delete`. Confirm clicking it (once a row is swiped
open) still deletes the row — it should, unchanged from Day 6 of Week 2.

Now the keyboard path, so this isn't mouse/touch-only:

```css
li:focus-within .row-content {
  transform: translateX(-88px);
}
```

- `:focus-within` — true when any descendant of the `<li>` has focus, including the
  Delete button itself. Tab through the page until focus reaches a Delete button —
  its row should slide open automatically, with no drag required. This is the
  accessible equivalent of swiping.

## 7. Break it deliberately (~10 min)

- Comment out `content.setPointerCapture(event.pointerId);`. Reload, drag a row
  slowly, then quickly flick your mouse far outside the row while still holding the
  button. The drag stops updating once the cursor leaves — put the line back and
  compare.
- Remove `content.style.transition = "none";` from `pointerdown` (keep the rest).
  Drag a row. It now feels sluggish, trailing behind your cursor instead of tracking
  it exactly, because the resting-state transition is fighting every intermediate
  value. Put it back.
- Remove `event: pan-y` — i.e. delete `touch-action: pan-y;` from `.row-content`. On a
  real touchscreen (or DevTools' touch simulation), a vertical scroll attempt near a
  row now feels like it's being hijacked. Put it back.
