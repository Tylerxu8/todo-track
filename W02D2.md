# W02D2 — Refactor: hold the list in a `tasks` array

**Goal:** the app stops reading its state from the DOM. A `tasks` array is the single
source of truth. Every action changes the array, then one `render()` function rebuilds
the list from it.

**Time budget:** ~90 min hands-on · ~15 min journal · ~15 min buffer

> Claude: explanations only. "Why is a single render function easier to reason about
> than patching the DOM in each handler?" is a fair question.

---

## 1. Why this refactor (~10 min)

Right now "is this task done?" is answered by looking at a CSS class. "What tasks
exist?" is answered by reading the DOM. That works for three features and collapses on
the fourth — and tomorrow you need `localStorage`, which needs your data as *data*,
not as markup.

The shape (from `W01D1`): `tasks` is an array of `{ id, text, done }`.

## 2. Introduce state and a renderer (~45 min)

```js
let tasks = [];
let nextId = 1;

function render() {
  list.innerHTML = '';
  for (const task of tasks) {
    const li = document.createElement('li');
    li.dataset.id = task.id;
    if (task.done) li.classList.add('done');

    const checkbox = document.createElement('input');
    checkbox.type = 'checkbox';
    checkbox.checked = task.done;

    const span = document.createElement('span');
    span.textContent = task.text;

    const del = document.createElement('button');
    del.type = 'button';
    del.className = 'delete';
    del.textContent = 'Delete';

    li.append(checkbox, span, del);
    list.appendChild(li);
  }
}
```

`li.dataset.id = task.id` puts `data-id="3"` on the element. That's the thread back
from a clicked row to its task object.

## 3. Rewrite the three handlers (~30 min)

Each one now changes `tasks` and calls `render()`. Nothing else touches the DOM.

- **Add** (in the submit handler, replacing your DOM-building code):

  ```js
  tasks.push({ id: nextId++, text, done: false });
  render();
  ```

- **Toggle** (in the `#list` click listener):

  ```js
  if (event.target.matches('input[type="checkbox"]')) {
    const id = Number(li.dataset.id);
    const task = tasks.find(t => t.id === id);
    task.done = !task.done;
    render();
  }
  ```

- **Delete:**

  ```js
  if (event.target.matches('button.delete')) {
    const id = Number(li.dataset.id);
    tasks = tasks.filter(t => t.id !== id);
    render();
  }
  ```

## 4. Test by hand (~5 min)

Same behavior as yesterday — add, toggle, un-toggle, delete. Nothing visible should
change. What changed is the direction: data → `render()` → screen, every time.

> **Foundations note — state vs the DOM.** One place holds the truth (`tasks`); the
> screen is a pure function of it. You never ask the DOM a question; you change the
> data and re-draw. Full write-up: `sidelines/state-vs-dom.md`.

---

## What "done" looks like for W02D2

- A `tasks` array and a `render()` function exist.
- No handler reads `classList` or the DOM to decide anything — they read/write
  `tasks`.
- All three actions end in `render()`.
- Behavior is identical to `W02D1`.
