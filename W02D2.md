# Week 2, Day 2 — Refactor: Hold the List in a `tasks` Array
*v1.1.0*

**Goal for today:** the app stops reading its state from the page. One array,
`tasks`, becomes the single source of truth. Every action changes the array, then one
`render()` function rebuilds the list from it. The behaviour won't change at all —
what changes is that the data now exists as data, which is what tomorrow's
`localStorage` needs.

**Time budget:** ~95 min hands-on, ~15 min journal, ~10 min slack.

## 2. Why refactor now — what and why (~15 min)

Right now, if you asked the app "what tasks exist?", the only way to answer is to
count the `<li>` elements currently on the page. "Is this one done?" is answered by
checking whether its `<li>` happens to carry the class `done`. In other words: **the
page itself is where your data lives.** There's no `tasks` variable anywhere — the
facts about your to-do list exist only as pixels and CSS classes.

That's fine for three features, and it falls apart on the fourth. Tomorrow you need
three things the page-as-database approach can't give you:

- **Save to `localStorage`** needs the tasks as plain data you can convert to text
  (`JSON.stringify`) — not as a tangle of HTML elements.
- **A "2 done" counter** needs to be computed from the list and kept in sync — awkward
  when the only copy of "the list" is scattered across DOM elements.
- **Loading saved tasks on startup** needs to turn data back into rows — which means
  you need a function that builds rows *from data* anyway, whether you call it today
  or tomorrow.

So today you build that function — `render()` — and make it the **only** thing that
ever writes to the `<ul>`. Everything else in the app will describe *what changed*,
and hand the actual describing-it-on-screen job to this one function.

Read `sidelines/state-vs-dom.md` now.

## 3. Add the state and the renderer — type it (~35 min)

At the **top** of `app.js`, just under the three `const` element lookups:

```js
let tasks = [];
let nextId = 1;

function render() {
  list.innerHTML = "";

  for (const task of tasks) {
    const li = document.createElement("li");
    li.dataset.id = task.id;
    if (task.done) li.classList.add("done");

    const checkbox = document.createElement("input");
    checkbox.type = "checkbox";
    checkbox.checked = task.done;

    const span = document.createElement("span");
    span.textContent = task.text;

    const del = document.createElement("button");
    del.type = "button";
    del.className = "delete";
    del.textContent = "Delete";

    li.append(checkbox, span, del);
    list.appendChild(li);
  }
}
```

Every line:

- `let tasks = []` — the array of `{ id, text, done }` objects from your Day 1 data
  model. `let`, not `const`, because — unlike `form`/`input`/`list`, which always
  point at the same three elements — this variable's *value* is going to be replaced
  outright, over and over, as tasks get added and removed.
- `let nextId = 1` — the id to hand the next new task. It only ever goes up, and
  never gets reused, exactly as you decided in the data model on Day 1.
- `function render() { ... }` — a named function this time (unlike the anonymous
  arrow functions inside `addEventListener` calls), because you're going to call it
  yourself, by name, from several different places, rather than handing it to
  something else to call automatically.
- `list.innerHTML = ""` — wipes out every child element currently inside `<ul
  id="list">`, leaving it completely empty. Then the loop below rebuilds it from
  scratch, every single time `render()` runs — even for a change as small as ticking
  one checkbox, the *entire* list is torn down and rebuilt. For a to-do list, this is
  cheap enough that it isn't worth optimizing; you just accept it as the trade for a
  much simpler mental model — you never have to figure out "which one row changed,"
  because you always just redraw everything.
- `for (const task of tasks) { ... }` — a **loop**: run everything inside the braces
  once for every item in `tasks`, with `task` standing in for "whichever one we're on
  right now" each time through. If `tasks` has three items, this body runs three
  times, each time with a different task's data available as `task`.
- Inside the loop, the rest is the exact row-building code you already wrote by hand
  on Day 5 and Day 6 — except now the values come from `task.id`, `task.text`, and
  `task.done` instead of being made up on the spot. `li.dataset.id = task.id` writes
  the id onto the element as a `data-id="..."` attribute — invisible on screen, but
  readable later by name, which is exactly the thread you'll need in the next step to
  connect a click back to the task it belongs to.
- `checkbox.checked = task.done` — this line is new and important: the checkbox's
  ticked state now comes **from the data**, every time `render()` runs, rather than
  being left however a click last set it. That means after a full rebuild, every
  checkbox still shows correctly — because it was told to, not because it happened to
  survive.

## 4. Rewrite the three handlers to go through state — type it (~35 min)

Now every handler does the same two steps: **change `tasks`, then call `render()`.**
None of them touch the DOM directly any more — they only ever touch the array, and
trust `render()` to make the screen match it.

**Add** — in the submit handler, replace everything from `const li = ...` down to
`list.appendChild(li);` with:

```js
  tasks.push({ id: nextId, text, done: false });
  nextId += 1;
  render();
```

- `.push(...)` is an **array method**: it adds one item onto the *end* of an array,
  in place. `tasks.push({...})` grows the array by exactly one task.
- `nextId += 1` is shorthand for `nextId = nextId + 1` — bump the counter so the next
  task gets a fresh, never-used id.

**Toggle and delete** — replace the body of the `list` click listener with:

```js
list.addEventListener("click", (event) => {
  const li = event.target.closest("li");
  if (!li) return;

  const id = Number(li.dataset.id);

  if (event.target.matches('input[type="checkbox"]')) {
    const task = tasks.find((t) => t.id === id);
    task.done = !task.done;
    render();
  }

  if (event.target.matches("button.delete")) {
    tasks = tasks.filter((t) => t.id !== id);
    render();
  }
});
```

- `li.dataset.id` reads back the `data-id` attribute you wrote in `render()`. All
  HTML attribute values are text, so this comes back as the **string** `"3"`, not the
  **number** `3` — even though you originally stored a number. `Number(...)` converts
  it back, which matters because `===` (JavaScript's "are these exactly equal"
  check) treats the string `"3"` and the number `3` as different things.
- `tasks.find((t) => t.id === id)` — another array method. `.find` walks the array
  and hands back the *first* item for which the little function you gave it
  (`(t) => t.id === id`) returns `true` — here, "the one task whose id matches." That
  small arrow function is called once per task in the array, each time with a
  different task as `t`, until one of them returns `true` (or the search runs out and
  gives back `undefined`).
- `task.done = !task.done` — `!` means "not," so this reads as "set done to whatever
  it currently *isn't*" — `true` becomes `false`, `false` becomes `true`. This is the
  one spot today where you're changing an existing object directly rather than
  building a new array — fine here, since `render()` will redraw from the result
  either way.
- `tasks.filter((t) => t.id !== id)` — `.filter` is a third array method: it builds
  and returns a **brand new array**, keeping only the items where your function
  returns `true`. Here: "keep every task whose id does *not* (`!==`) match — throw
  away the one that does." `tasks = ...` then replaces the whole variable with that
  new, shorter array. Notice `tasks` had to be declared with `let`, not `const`,
  precisely so this reassignment is allowed.

Finally, at the very bottom of `app.js`, add one line so the (empty) list renders on
first load:

```js
render();
```

  entire mental model of today's refactor in miniature. Put `render()` back.
