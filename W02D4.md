## 2. localStorage — what and why (~15 min)

`localStorage` is a small storage locker the browser gives to every website, kept on
your disk. Unlike your `tasks` variable — which lives only in the computer's memory
and is thrown away the instant you close or refresh the tab — anything you put in
`localStorage` is still there the next time you visit, even after fully quitting the
browser.

The catch: **it only stores text.** Not arrays, not objects — plain strings, always.
Both the "key" you save something under and the "value" you save must be strings.
That's exactly why yesterday was about JSON: it's the tool that turns your `tasks`
array into a string (to save it) and back into a real array again (to load it).

The whole API you need:

```js
localStorage.setItem("todo-track", "...some string...");   // write
localStorage.getItem("todo-track");                        // read -> string, or null
```

Read `sidelines/localstorage.md` now — specifically "The two things that bite."

## 3. Save on every change — type it (~15 min)

Add a `save` function near the top of `app.js`, after `render`:

```js
function save() {
  localStorage.setItem("todo-track", JSON.stringify(tasks));
}
```

This is only two things chained together: turn `tasks` into a JSON string
(`JSON.stringify`), then hand that string to `localStorage` under the key
`"todo-track"` (a name you're choosing, purely so you can find it again later — it
could be any string, as long as you use the same one every time).

Then call it at the end of `render()` — every action already ends in `render()`, so
this one line covers add, toggle, and delete at once. Add as the last line inside
`render`, after the `for` loop:

```js
  save();
```

Test: add two tasks. Open DevTools → **Application** → **Local Storage** →
your file's origin. You should see a `todo-track` key whose value is a JSON string like
`[{"id":1,"text":"a","done":false},{"id":2,"text":"b","done":false}]` — that long
string of text is your entire to-do list, in its saved form.

Refresh the page. The tasks still vanish — because you're *saving* but not yet
*loading*. That's the next step.

## 4. Load on startup, with the guards — type it (~30 min)

Replace the bare `render();` at the bottom of `app.js` with this block:

```js
const saved = localStorage.getItem("todo-track");
if (saved) {
  try {
    tasks = JSON.parse(saved);
    nextId = Math.max(0, ...tasks.map((t) => t.id)) + 1;
  } catch {
    tasks = [];
  }
}
render();
```

Every line, because every line is defending against something real:

- `const saved = localStorage.getItem("todo-track")` — the stored string, or `null`
  (JavaScript's "nothing here") on a first-ever visit, when that key has never been
  written.
- `if (saved)` — skip everything inside if there's nothing stored. Trying to
  `JSON.parse(null)` would throw an error and stop your whole script.
- `try { ... } catch { tasks = []; }` — a **try/catch block**. Everything inside
  `try { }` is code that *might* fail — here, `JSON.parse` will throw an error if the
  text it's given isn't valid JSON. Normally, an error stops your script cold, right
  there, and everything after it never runs. Wrapping risky code in `try` means: "if
  this fails, don't crash the whole page — instead, jump straight to the `catch`
  block and run *that* instead." The stored string genuinely can turn into garbage: a
  half-write from a crash, something you edited by hand in DevTools, a browser
  extension that touched it. A to-do app that shows a blank white screen because its
  storage got corrupted is worse than one that quietly starts empty — so the `catch`
  block's job is simply "give up gracefully and start fresh," rather than let the
  whole app die.
- `tasks = JSON.parse(saved)` — the line that can fail: turn the saved string back
  into a real array.
- `nextId = Math.max(0, ...tasks.map((t) => t.id)) + 1` — after loading old tasks
  back in, the next id you hand out must be higher than every id already present, or
  you'd eventually create two tasks with the same id. `tasks.map((t) => t.id)`
  collects just the ids into their own array (say, `[1, 2, 5]`). The `...` in front
  of it "spreads" that array out into separate arguments, so
  `Math.max(0, ...[1, 2, 5])` is really `Math.max(0, 1, 2, 5)` — a built-in function
  that returns the largest of everything handed to it. Adding `1` gives the next free
  id. **The `0` at the front is load-bearing:** `Math.max()` called with nothing at
  all returns a special value called negative infinity, so on a brand-new, empty
  list this line would set `nextId` to that instead, without the `0` acting as a
  guaranteed floor. (You'll see exactly this bug, planted on purpose, in `broken/`
  tomorrow.)
- `render()` — draw whatever you ended up with, whether it's the loaded tasks or a
  clean empty list from the `catch` block.

Test: add tasks, refresh — **they're still there.** Quit the browser completely,
reopen, navigate back to the file — still there.

## 5. Edge cases (~25 min)

**Long text.** Add a task of 300+ characters (mash the keyboard). Does the row hold
its shape, or does the text shove the Delete button off-screen? If it breaks the
layout, add to `styles.css`:

```css
#list li span {
  overflow-wrap: anywhere;
}
```

Re-test at 360px width too.

**A task counter.** Add a `<p id="counter"></p>` in `index.html`, between the form and
the `<ul>`. Select it at the top of `app.js`:

```js
const counter = document.querySelector("#counter");
```

Then, inside `render()`, just before `save();`:

```js
  const doneCount = tasks.filter((t) => t.done).length;
  counter.textContent = `${tasks.length} tasks · ${doneCount} done`;
```

- `tasks.filter((t) => t.done)` — the same `.filter` method from Day 7, this time
  keeping only the tasks whose `done` is `true`. `.length` on the result gives you
  the count.
- The backtick-quoted text `` `${tasks.length} tasks · ${doneCount} done` `` is a
  **template literal**: a string that can have live values dropped into it with
  `${...}`, instead of stitching pieces together with `+`. It reads much closer to
  the sentence you actually want.

Because this whole block lives *inside* `render()`, it recomputes from `tasks`
every single time the list redraws — add, toggle, or delete, the counter is never
computed anywhere else, so it can never drift out of sync with the real list.

## 6. Break it deliberately (~10 min)

- DevTools → Application → Local Storage → double-click the `todo-track` value, replace
  it with `{{{ broken`, press Enter, reload the page. The app should start **empty**,
  not error. Check the Console is clean.
- Now temporarily delete the `try` / `catch` (just `tasks = JSON.parse(saved);`).
  Corrupt the value again, reload. Now you get an uncaught `SyntaxError` in the
  Console and `render()` never runs — blank app. Put the `try/catch` back. This is
  exactly the failure the guard prevents.
