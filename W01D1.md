# Week 1, Day 1 — Setup, the Sketch, and the Data Model
*v1.0.0*

**Goal for today:** get a working repo, draw the app on paper, and write down — in
plain words — how the app represents a task as *data*. Nothing runs yet. Every line of
code you write over the next two weeks grows out of the three-field object you define
today.

**Time budget:** ~90 min hands-on, ~15 min journal, ~15 min slack.

---

## 1. Warm-up (~10 min)

There's no "yesterday" yet, so today's warm-up is orientation.

- Open the repo in your terminal:
  ```
  cd ~/dev/todo-track
  ```
- Read `README.md` end to end. It's the map for the next ten days. Pay attention to
  the AI table — this week you get **no AI at all**, not for code and not for
  explanations, and the reason is stated in the README.
- Run `git status`. It should say `nothing to commit, working tree clean` (the

  continuing — an unclean tree on day one means something already went sideways.
- Run `git log --oneline`. You should see one commit: the scaffold.

## 2. Why this project has no toolchain (~10 min)

A note on what you're deliberately *not* doing.

This app is plain HTML, CSS, and JavaScript that runs directly in a browser. There is
no `npm install`, no build step, no framework, no `node_modules/`. You open an HTML
file and it works. That choice keeps every moving part visible: when something breaks,
the cause is in one of three files you wrote — not in a tool's config or a
dependency's version.

The one place a tool appears is Week 2 Day 5, where you run a local web server and
Node's test runner. Both are built in. Nothing to install, ever.

So there's no environment to "activate." The whole setup is: a folder, a git repo, and
a browser.

## 3. Sketch the app on paper (~20 min)

Real paper, real pen. Screens you design in your head have no edges; paper forces
decisions.

Draw the whole screen:

- A title at the top.
- A single-line text box, and an **Add** button next to it.
- Below that, a vertical list of tasks.
- One task row, drawn in detail: the task text, something to mark it done, something
  to delete it. Decide **now** whether "mark done" is a checkbox, a tap on the text,
  or a button — and draw the one you picked.

Then draw a second copy of a single row in its **done** state. Crossed out? Greyed?
Checkbox filled? Draw exactly what "done" looks like, because on Day 4 you write the
CSS that has to match this drawing.

Photograph the sketch. Save it into the repo as `journal/sketch.jpg`.

> Why this counts as work: the sketch is your first **oracle** — the thing you compare
> the real app against. On Days 4 and 5, "is this right?" will mean "does it match the
> sketch?"

## 4. Write the data model — what and why (~25 min)

Here is the central idea of the whole track: **the screen is a picture of some data.**
Get the data right and the screen is easy to build. Try to skip the data and keep
everything "in the page" — deciding whether a task is done by checking whether its row
looks grey — and every feature after the second one fights you.

So, before any code, you decide the data. Create `journal/data-model.md` and type this
(don't paste):

```
# Data model

## A task
A task is an object with three fields:

- id    a number, unique per task. Never shown to the user. It exists so the app
        can point at one specific task even when two tasks have identical text.
- text  a string. Exactly what the user typed (after trimming spaces).
- done  a boolean. false when created; flips when the user marks it done.

Written out:  { id: 1, text: "buy milk", done: false }

## The list
The whole to-do list is an array of task objects, in the order they were added:

  [
    { id: 1, text: "buy milk",      done: false },
    { id: 2, text: "call the bank", done: true  }
  ]

## The three operations
1. ADD    take the typed text, make { id: <next unused id>, text, done: false },
          put it on the END of the array.
2. TOGGLE given an id, find that task, set done to the opposite of what it is.
3. DELETE given an id, remove the task with that id from the array.

## A decision I am making now
id is a plain incrementing number (1, 2, 3, ...). Not a random string, not the
text itself. If the user deletes task 2, the next new task is still 3 — ids are
never reused.
```

Read your own file back. Every code decision for the next two weeks traces to
something on this page.

> **Why `id` at all?** Say the user adds "call mum" twice. Two rows, identical text.
> The user ticks the second one. The app must change *that* task's `done` and not the
> first one's. Text can't tell them apart; position in the list changes when things
> are deleted; an `id` is stable and unique. Using the text or the row position as the
> identity is the single most common beginner mistake in a to-do app, and you're
> designing it out on day one.

## 5. Stub the entry point (~15 min)

The app needs a file to open. Create `src/index.html` and type this exactly:

```html
<!doctype html>
<html lang="en">
<head>
  <meta charset="utf-8">
  <meta name="viewport" content="width=device-width, initial-scale=1">
  <title>Todo</title>
</head>
<body>
  <h1>Todo</h1>
  <!-- the form and the list arrive on Day 2 -->
</body>
</html>
```

Line by line, so you could have written it:

- `<!doctype html>` — tells the browser "modern HTML, use standards mode." Without it,
  browsers fall back to a 1990s compatibility mode that breaks CSS in subtle ways.
- `<html lang="en">` — declares the page language. Screen readers use it to choose a
  voice; search engines use it too.
- `<meta charset="utf-8">` — says the text is UTF-8, so `—` and `é` render instead of
  turning into garbage characters.
- `<meta name="viewport" ...>` — tells phones "render at device width, don't pretend
  to be a 980px desktop and zoom out." Every mobile-friendly page has this line.
- `<title>Todo</title>` — the browser-tab label.
- `<h1>Todo</h1>` — the one top-level heading. A page has exactly one `<h1>`.

Open it:

```
open src/index.html
```

You should see a white page with **Todo** in large bold text. That is the correct
result for today.

Now break it deliberately. Reload after each change, then undo it:

- Delete the `<!doctype html>` line, reload. (Looks the same for now — the damage only
  shows once there's CSS. Note that it looked fine anyway; that's the trap.)
- Change `<title>Todo</title>` to `<title>Groceries</title>`, reload. Watch the tab,
  not the page.
- Delete the closing `</h1>`, reload. Does the browser complain, or does it quietly
  guess what you meant?

Put all three back.
