## 2. Why "semantic" HTML — what and why (~10 min)

You could build this whole app out of `<div>`s — a `<div>` is HTML's generic,
meaning-free box, usable for absolutely anything. Lots of people do it that way. Here
is why we won't.

Some HTML tags carry built-in *behavior and meaning* that the browser (and assistive
technology, like screen readers for people who can't see the screen) already
understands, for free, with zero code from you:

- A `<form>` submits when you press Enter in a text field inside it. A `<div>` doesn't
  — it's just a box, it has no concept of "submitting."
- A `<button type="submit">` triggers that submit. A clickable `<div>` needs
  JavaScript written specially to react to a click at all, and by default a screen
  reader has no idea it's meant to be pressed.
- A `<label>` tied to an input makes the label text clickable, and makes a screen
  reader announce "New task, edit text" instead of just "edit text."
- A `<ul>` (an HTML "unordered list") tells a screen reader "list, 4 items," so
  someone using one knows how much content is coming before they dive in.

Choosing the tag that already means the right thing is the cheapest robustness you'll
ever get in this project.

## 3. Build the form (~30 min)

In `src/index.html`, replace the `<!-- the form and the list arrive on Day 2 -->`
comment with a form. Type it:

```html
<form id="new-task">
  <label for="task-input">New task</label>
  <input type="text" id="task-input" name="task" autocomplete="off">
  <button type="submit">Add</button>
</form>
```

A quick vocabulary note before the line-by-line: the bits inside a tag like
`id="new-task"` are called **attributes** — extra information attached to a tag,
always written as `name="value"`. A tag can have several. You'll see attributes
constantly from here on; they're just labeled settings on an element.

Now every attribute here, and why it's there:

- `id="new-task"` on the form — a hook for JavaScript on Day 5. An `id` is a unique
  name you give one specific element so your code (or your CSS) can find that exact
  element later, out of everything else on the page — like giving one specific box in
  a warehouse a label so a forklift driver can find it without opening every box.
- `<label for="task-input">` — the `for` value must **exactly** match the input's
  `id`, below. That matching pair is the entire link between them; nothing else
  connects a label to its input.
- `type="text"` — a single-line text field. (There are roughly 20 different `type`
  values for `<input>` — `checkbox`, `date`, `email`, and more, each with its own
  built-in appearance and behavior. This is the plain one.)
- `id="task-input"` — the JavaScript hook, and the label's target.
- `name="task"` — the field's name if this form were ever submitted to a server the
  old-fashioned way. We won't, but leaving `name` off a real form field is a bad
  habit.
- `autocomplete="off"` — stop the browser offering a dropdown of things you typed
  before; it's noise for a to-do box.
- `type="submit"` on the button — **this is the important one.** A submit button,
  when clicked or when Enter is pressed anywhere in the text field, fires the form's
  `submit` event. An **event** is just "something happened that the page can react
  to" — a click, a keypress, a submit. You'll spend a lot of Week 2 reacting to
  events; this is the first one you'll wire up, on Day 5.

Save, reload. You'll see the label, a text box, and an Add button, stacked awkwardly
and unstyled. That's correct — styling is Day 4.

## 4. See the default behaviour, so you understand what you'll override (~15 min)

Type "buy milk" in the box and press Enter.

The page **reloads.** Look at the URL bar — it now ends with `?task=buy+milk`. That is
the browser's own, automatic response to a form submit: gather up the fields, stick
them on the end of the URL, and load the page fresh, as if you'd typed that whole URL
in yourself.

You don't want that — you want the page to quietly add a row and stay exactly where
it is. On Day 5 the very first line of code you write for this form will be
`event.preventDefault()`, which is JavaScript's way of saying "browser, don't do your
usual automatic thing this time — I'm handling it myself." Seeing the automatic
reload now is what will make that line make sense later; right now, nothing is
stopping the browser from doing what it always does by default.

Try two variations:

- Click the **Add** button instead of pressing Enter. Same reload — that's
  `type="submit"`.
- Temporarily change the button to `type="button"`, reload, click it. **No reload** —
  a plain button submits nothing; it has no built-in behavior at all until you write
  some. Change it back to `type="submit"`.

## 5. Add the list, and a temporary sample row (~20 min)

Below the form:

```html
<ul id="list">
  <li>
    <input type="checkbox">
    <span>Buy milk</span>
    <button type="button" class="delete">Delete</button>
  </li>
</ul>
```

- `<ul id="list">` — the empty container. Day 5's JavaScript fills it. A `<ul>` may
  only contain `<li>` (list item) children directly, so never put anything else
  straight inside it.
- The `<li>` inside it is **scaffolding** — a hardcoded example row so you have
  something to style on Day 4, standing in for what real rows will look like once
  JavaScript is building them. It has the exact shape every real row will have:
  - a checkbox (mark done),
  - a `<span>` holding the task text — `<span>` is a generic, meaning-free *inline*
    tag (it doesn't force a line break the way `<div>` or `<p>` would), used here
    purely as a labeled place to put text so JavaScript can find and change it later,
  - a `<button type="button" class="delete">` — `type="button"` because it is **not**
    submitting the form (that's what `type="submit"` is for), and `class="delete"` is
    a second kind of label: unlike `id`, a `class` can be reused on many elements at
    once, which is exactly what happens once every row has its own Delete button. Day
    6's click handler will use `class="delete"` to recognize any of them.

Write one line in your journal now: **"delete the sample `<li>` on W01D5."** You will
forget otherwise, and a hardcoded "Buy milk" that never goes away is a confusing bug
to chase a week later.

Save, reload. You now have a form and one fake task row.
