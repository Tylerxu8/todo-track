## 3. Extract the pure functions into a module — type it (~25 min)

A **module** is just a JavaScript file that explicitly says which of its own pieces
other files are allowed to use. Up to now, everything in `app.js` has been one big
file where every line can see every other line. Splitting the pure logic out into its
own file keeps it usable — and testable — completely on its own, with no dependency
on the page at all.

Create `src/todo.js` with the three pure functions you designed on Day 3:

```js
export function addTask(tasks, text, id) {
  return [...tasks, { id, text, done: false }];
}

export function toggle(tasks, id) {
  return tasks.map((t) => (t.id === id ? { ...t, done: !t.done } : t));
}

export function remove(tasks, id) {
  return tasks.filter((t) => t.id !== id);
}
```

- `export` in front of a function means "other files are allowed to `import` this
  one." Without it, a function is private to the file it's written in — the same
  idea as marking something public versus keeping it to yourself.
- Each function returns a **new** array and changes nothing it was handed — the
  "vending machine" behavior from Day 3 — which is exactly what makes them testable
  in step 4 with no browser involved at all.

Now wire them into `app.js`. At the very top:

```js
import { addTask, toggle, remove } from "./todo.js";
```

- `import { addTask, toggle, remove } from "./todo.js"` — the other half of
  `export`: "bring these three specific names in from that file, and let me use them
  here as if I'd written them myself." `"./todo.js"` — the `./` and the `.js` are
  both **required** in browser modules (unlike some other JavaScript environments).
  Leave either off and the import silently fails to find the file.

Then use them in the handlers, replacing the inline array work:

```js
// add (in the submit handler)
tasks = addTask(tasks, text, nextId);
nextId += 1;
render();

// toggle branch
tasks = toggle(tasks, id);
render();

// delete branch
tasks = remove(tasks, id);
render();
```

Note the toggle branch changes shape: instead of finding a task and mutating
`task.done` directly, you now replace the whole array with the *result of calling*
`toggle(tasks, id)` — a brand new array, handed back and stored over the old one.
That's the pure style in practice: nothing is changed in place; everything is
replaced with a fresh copy that has the one difference you wanted.

Finally, change the script tag in `index.html`:

```html
<script type="module" src="app.js"></script>
```

(`type="module"` tells the browser "this file uses `import`/`export`" — and drop
`defer`; modules already wait for the page to finish loading automatically, the same
behavior `defer` used to give you by hand.)

## 4. Run a local server (~10 min)

`type="module"` scripts **will not load from a `file://` URL** — the browser blocks it
for security, since modules can request other files, and that's treated as too risky
to allow from a page opened straight off disk. Open the app from now on via a local
server instead — a tiny, temporary web server running on your own machine that serves
your files the same way a real website would:

```
cd ~/dev/todo-track/src
python3 -m http.server 8000
```

Open <http://localhost:8000>. The app should work exactly as before. If the imports
error in the Console, this is where you may lean on Claude Code — but read the diff.

> Note: `localhost:8000` is a different **origin** from the `file://` you used all
> week (an origin is, roughly, "which website" — even two ways of viewing your own
> files count as different websites to the browser), so `localStorage` is a fresh,
> empty store here. Your earlier test tasks aren't gone — they're just filed under
> the old origin. This is expected.

## 5. Tests — type the structure, lean on Claude Code for extra cases if you want (~30 min)

A **unit test** is a small, automatic check: "call this function with a known input,
and confirm the result is exactly what I expect." Instead of manually clicking
through the app to check your logic every time you change something, you write the
check once, and re-run it in a second.

Create `tests/test.js`:

```js
import assert from "node:assert/strict";
import { addTask, toggle, remove } from "../src/todo.js";

let passed = 0;
function test(name, fn) {
  fn();
  passed += 1;
  console.log("ok -", name);
}

test("addTask appends one task with done:false", () => {
  const out = addTask([], "buy milk", 1);
  assert.equal(out.length, 1);
  assert.equal(out[0].text, "buy milk");
  assert.equal(out[0].done, false);
});

test("addTask does not mutate its input array", () => {
  const input = [];
  addTask(input, "x", 1);
  assert.equal(input.length, 0);
});

test("toggle flips done for the matching id only", () => {
  const start = [
    { id: 1, text: "a", done: false },
    { id: 2, text: "b", done: false },
  ];
  const out = toggle(start, 1);
  assert.equal(out[0].done, true);
  assert.equal(out[1].done, false);
});

test("remove drops the task with that id", () => {
  const start = [
    { id: 1, text: "a", done: false },
    { id: 2, text: "b", done: false },
  ];
  const out = remove(start, 1);
  assert.equal(out.length, 1);
  assert.equal(out[0].id, 2);
});

console.log(`\n${passed} passed`);
```

- `assert.equal(a, b)` is called an **assertion** — a statement that "these two values
  had better be equal, or something is wrong." If they match, nothing happens and the
  code continues. If they don't, `assert.equal` **throws an error immediately**,
  which stops that test and prints out exactly what it expected versus what it
  actually got. That's the whole mechanism a test suite is built on: a pile of small,
  specific claims about what the code should do, each one capable of loudly failing
  the instant it turns out to be wrong.
- `function test(name, fn) { fn(); ... }` is a tiny helper you're writing yourself,
  purely to keep the file tidy: it takes a label and a function, runs the function
  (which is where the real checking — the `assert.equal` calls — happens), and prints
  a line confirming it ran. If any `assert.equal` inside `fn()` throws, `fn()` never
  finishes, `passed` never increments for that test, and the error interrupts the
  whole file — that interruption *is* your failure signal.

Run it:

```
cd ~/dev/todo-track
node tests/test.js
```

You want `4 passed`. Then **add one more test of your own** — a case you actually care
about (e.g. "toggle twice returns to the original state", "remove with an id that
isn't there changes nothing").

### green → red → green (~10 min, inside the 30)

With tests passing: go into `src/todo.js` and deliberately break `toggle` — change
`!t.done` to `t.done`. Run the tests. Watch **which** test fails and read the
assertion message: it tells you exactly what it expected versus what it got. Then undo
the change and confirm green again.

That's the loop, and the rule from step 2: a red test is a precise question about a
difference between what you expected and what the code does. You diagnose it. You don't
delete it.

step 4), anyone with a link can load them straight from the internet.

   `git mv src docs` locally, fix nothing else (paths are all relative), commit, push.

5. Your URL is `https://tylerxu8.github.io/todo-track/`. Open it **on your phone.** Add
