## 2. The new shape — what and why (~15 min)

Today, `tasks` is a flat array — one list, no grouping. From today, it becomes a list
of **lists**, each one holding its own tasks:

```
lists = [
  { id: 1, name: "My List", tasks: [ {id, text, done, dueDate, flagged}, ... ] },
  { id: 2, name: "Groceries", tasks: [ ... ] },
]
activeListId = 1   // which list is currently shown on screen
```

Notice this is just objects and arrays *nested inside each other* — an array of
`list` objects, and each `list` object has its own `tasks` array inside it, exactly
the same kind of array you've had since Week 1. Nothing new is introduced here beyond
"an array can hold anything, including other objects that themselves contain arrays."

The task-level pure functions you already have — `addTask`, `toggle`, `remove`,
`setDueDate`, `toggleFlag` — all operate on a plain tasks array, and take that array
in as a plain argument rather than reaching out to some global variable to find it.
**None of them need to change today.** You'll add a small set of list-level functions
that operate on `lists` instead, and `app.js` will compose the two together: pull the
active list's tasks back out of `lists`, run one of your existing functions on that
plain array exactly as before, then put the (new) result back into `lists`. This is
the direct payoff of writing those functions the way you did back on `W02D3` — because
they only ever look at what you hand them, they don't care whether that array came
from a simple `tasks` variable or from deep inside a bigger structure.

## 3. Add list-level pure functions to `todo.js` — type it (~25 min)

```js
export function addList(lists, name, id) {
  return [...lists, { id, name, tasks: [] }];
}

export function removeList(lists, id) {
  return lists.filter((l) => l.id !== id);
}

export function findList(lists, id) {
  return lists.find((l) => l.id === id);
}

export function replaceListTasks(lists, id, tasks) {
  return lists.map((l) => (l.id === id ? { ...l, tasks } : l));
}
```

- `addList`, `removeList` mirror `addTask`/`remove` exactly, just one level up — same
  spread-to-add, same filter-to-remove pattern, applied to `lists` instead of
  `tasks`.
- `findList` isn't strictly "pure" by the strictest definition (it can return
  `undefined` if nothing matches, rather than a predictable, always-present value) —
  but it still takes only its arguments and changes nothing, which is good enough,
  and it's still trivially testable.
- `replaceListTasks` is the connector piece, and the one genuinely new idea today:
  "here's a whole new tasks array for one specific list; give me back the whole
  `lists` structure with that one list updated and every other list left completely
  untouched." `{ ...l, tasks }` copies every field of `l` (its `id`, its `name`), then
  overwrites just `tasks` with the new array you're passing in. Every task action from
  here on will go through this function.

Add tests for all four in `tests/test.js`, following the shape of your existing tests
— at minimum: `addList` appends without mutating, `removeList` drops the right one,
`replaceListTasks` updates only the targeted list.

## 4. The migration — what and why (~20 min)

Anyone who used the app before today has a `todo-track` key in `localStorage` holding
a flat array — the old shape. If you switch straight over to reading a *new* key
today, that old data isn't actually erased from the disk — but the app will never
look at it again, and from the user's point of view, it's exactly as if it vanished
without warning. **Migrating** means: on the very first run of today's new code,
detect the old shape if it's there, and automatically convert it into the new shape,
so nothing the user already built gets lost.

At the top of `app.js`, where you currently load from `localStorage`, replace it with:

```js
let lists = [];
let activeListId = 1;
let nextListId = 2;
let nextTaskId = 1;

const savedLists = localStorage.getItem("todo-track-lists");
const savedFlat = localStorage.getItem("todo-track"); // the old, pre-Week-3 shape

if (savedLists) {
  try {
    const parsed = JSON.parse(savedLists);
    lists = parsed.lists;
    activeListId = parsed.activeListId;
  } catch {
    lists = [{ id: 1, name: "My List", tasks: [] }];
  }
} else if (savedFlat) {
  try {
    const oldTasks = JSON.parse(savedFlat);
    lists = [{ id: 1, name: "My List", tasks: oldTasks }];
  } catch {
    lists = [{ id: 1, name: "My List", tasks: [] }];
  }
} else {
  lists = [{ id: 1, name: "My List", tasks: [] }];
}

const allIds = lists.flatMap((l) => l.tasks.map((t) => t.id));
nextTaskId = Math.max(0, ...allIds) + 1;
nextListId = Math.max(0, ...lists.map((l) => l.id)) + 1;
```

Walk it slowly — this is the densest block of the whole track, but every piece is
something you've already used:

- **Three cases, checked one after another with `if` / `else if` / `else`:** does the
  new format already exist? (a returning Week-3 user, nothing to migrate). If not,
  does the *old* flat format exist? (a migration is needed, right now, this run). If
  neither exists? (a brand-new user; start empty.) Only one of the three branches
  ever runs.
- Each branch that reads saved data wraps it in its own `try`/`catch`, following
  `W02D4`'s rule: if the stored text turns out to be corrupt JSON, fall back to a
  single clean empty list rather than crashing.
- **The migration itself is one line:** `lists = [{ id: 1, name: "My List", tasks:
  oldTasks }]`. Nothing is being computed or transformed — you're simply taking the
  entire old flat array and placing it, as-is, inside a brand-new list object called
  "My List." Every task the user had is still there, just re-homed one level deeper
  in the structure.
- `lists.flatMap((l) => l.tasks.map((t) => t.id))` — this line collects every task
  id, across *every* list, into one single flat array of numbers. `.map` alone would
  give you an array of arrays (one array of ids per list); `.flatMap` is the same
  idea as `.map`, except it automatically flattens the arrays-within-an-array into
  one single, level array afterward. You need this because ids must stay globally
  unique even though tasks now live scattered across separate lists.
- `nextTaskId` and `nextListId` are then both computed with the same
  `Math.max(0, ...)` pattern from `W02D4` — the `0` still matters for exactly the same
  reason as before (an empty list of ids would otherwise produce negative infinity).
- **You are not deleting the old `todo-track` key.** Leave it exactly where it is.
  If there turns out to be a bug in your migration logic, the original data is still
  sitting there, completely intact, and recoverable. (You could add cleanup later,
  once you've used the app for a while and trust it.)

Update `save()` to write the new shape and stop writing the old one:

```js
function save() {
  localStorage.setItem(
    "todo-track-lists",
    JSON.stringify({ lists, activeListId })
  );
}
```

## 5. Rewire the handlers through the active list (~25 min)

Every place that used to say `tasks = someFunction(tasks, ...)` now needs to: find the
active list, run the function on *its* tasks, write the result back into `lists`.

```js
function currentTasks() {
  return findList(lists, activeListId).tasks;
}

function updateCurrentTasks(newTasks) {
  lists = replaceListTasks(lists, activeListId, newTasks);
}
```

These two small helper functions are the only new "glue" you're writing — everything
else keeps calling the same pure functions from before, just through this glue
instead of directly on a bare `tasks` variable.

For example, your submit handler goes from:

```js
tasks = addTask(tasks, text, nextId);
```

to:

```js
updateCurrentTasks(addTask(currentTasks(), text, nextTaskId));
nextTaskId += 1;
```

Read the inner-to-outer order: first `currentTasks()` gets the active list's current
array; `addTask(...)` runs on that array exactly like it always has, returning a new
array with one more task; `updateCurrentTasks(...)` takes that new array and slots it
back into `lists` in place of the old one. `addTask` itself never had to change at
all — it doesn't even know `lists` exists.

Apply the same pattern to every handler that touches tasks: toggle, delete,
`setDueDate`, `toggleFlag`. And update `render()` to read from `currentTasks()`
instead of a `tasks` variable — remove the standalone `let tasks` entirely; `lists`
is now the only source of truth.

## 6. Build the list-switcher UI (~15 min)

Add above the form in `index.html`:

```html
<div id="list-tabs"></div>
```

In `app.js`, inside (or just before) `render()`, rebuild the tabs each time too:

```js
function renderTabs() {
  const tabs = document.querySelector("#list-tabs");
  tabs.innerHTML = "";

  for (const l of lists) {
    const btn = document.createElement("button");
    btn.type = "button";
    btn.textContent = l.name;
    btn.className = l.id === activeListId ? "tab active" : "tab";
    btn.dataset.listId = l.id;
    tabs.appendChild(btn);
  }

  const addBtn = document.createElement("button");
  addBtn.type = "button";
  addBtn.textContent = "+";
  addBtn.id = "add-list";
  tabs.appendChild(addBtn);
}
```

- `btn.className = l.id === activeListId ? "tab active" : "tab"` uses the **ternary
  operator**: `condition ? valueIfTrue : valueIfFalse` — a compact `if`/`else` that
  produces a value instead of running separate blocks of code. Read it as: "if this
  list's id matches the active one, use both classes; otherwise, just the plain
  one."

Call `renderTabs()` everywhere you call `render()`.

Wire the clicks (a new delegated listener, same pattern as `W02D1`):

```js
document.querySelector("#list-tabs").addEventListener("click", (event) => {
  if (event.target.matches(".tab")) {
    activeListId = Number(event.target.dataset.listId);
    render();
    renderTabs();
  }

  if (event.target.id === "add-list") {
    const name = prompt("List name?");
    if (!name || !name.trim()) return;
    lists = addList(lists, name.trim(), nextListId);
    nextListId += 1;
    activeListId = nextListId - 1;
    render();
    renderTabs();
  }
});
```

- `prompt(...)` is a built-in browser function that pops up a small native dialog box
  asking the user to type something, and pauses your code until they answer. It's a
  quick, unstyled, and entirely legitimate choice here — it needs no HTML of its own
  and blocks until you get an answer. A real product would build a nicer-looking
  input instead; skipping that for a to-do app is a fair scope decision, not
  laziness.

Minimal styling:

