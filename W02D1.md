## 3. Why not one listener per row — what and why (~15 min)

The obvious approach: when you build a row in the submit handler, also attach a
separate click listener directly onto that row's checkbox, and another onto its
Delete button, the moment you create them.

It works, and it's a trap, for two concrete reasons:

- Every new task means two more listeners living in memory. A hundred tasks, two
  hundred listeners — not a huge amount for a to-do list, but the pattern doesn't
  scale, and you'll rebuild the whole list from scratch tomorrow, which would mean
  re-attaching all of them, every time, correctly, in order.
- The logic for "what does delete do" ends up scattered across the row-builder,
  tangled up with the `createElement` calls, instead of living in one obvious place.

The better approach relies on something browsers do automatically: when you click a
button *inside* a row, that click doesn't only happen "on the button" — it also
**bubbles up** through every ancestor element above it (the `<li>`, then the `<ul>`,
then `<body>`, and so on), as if the click event were rippling outward like a wave.
A listener on any of those ancestors can catch it on the way past. So instead of one
listener per row, you put **one** `click` listener on `<ul id="list">` itself — which
never gets rebuilt — and every click on every row, present or future, ripples up
through it. This technique is called **event delegation**: delegating the handling of
many elements' clicks to one listener on a shared parent. Read `sidelines/events.md`
section "Bubbling and delegation" now if you want the fuller version.

## 4. The delegated listener — type it, don't paste (~35 min)

Add this to `app.js`, below the submit handler:

```js
list.addEventListener("click", (event) => {
  const li = event.target.closest("li");
  if (!li) return;

  if (event.target.matches('input[type="checkbox"]')) {
    li.classList.toggle("done");
  }

  if (event.target.matches("button.delete")) {
    li.remove();
  }
});
```

Every line, so you own it:

- `list.addEventListener("click", ...)` — one listener, on the container, exactly as
  planned above.
- `event.target` — every event object carries this: the *exact* element that was
  actually clicked. If you click the Delete button, `event.target` is that button —
  not the `<li>` around it, not the `<ul>` the listener is attached to.
- `event.target.closest("li")` — a method that starts at `event.target` and walks
  **upward** through its ancestors, stopping at the nearest one matching the given
  selector (including `event.target` itself, if it already matches). In other words:
  "whatever I clicked, find the row it belongs to." Returns that `<li>`, or `null` if
  the click wasn't inside any `<li>` at all.
- `if (!li) return;` — the `!` means "not." So: "if there's no matching row, stop —
  nothing to do." This covers clicking somewhere in the empty space of the `<ul>`
  itself, between rows.
- `event.target.matches('input[type="checkbox"]')` — another method on the clicked
  element: "does this element match this CSS selector?" Returns `true` or `false`.
  Here: "was the thing I clicked specifically a checkbox?"
- `li.classList.toggle("done")` — `classList` is a small built-in toolbox every
  element has for managing its CSS classes. `.toggle("done")` adds the class if it's
  currently missing, or removes it if it's currently present — flipping it, the same
  way a light switch flips. The CSS rule from Day 4 (`#list li.done span`) reacts to
  that class appearing or disappearing.
- `event.target.matches("button.delete")` — "was the thing I clicked the Delete
  button?" (an element that is both a `<button>` *and* carries the class `delete`).
- `li.remove()` — a method that detaches an element (and everything inside it) from
  the page entirely. The row visually disappears the instant this runs.

## 6. Break it deliberately (~10 min)

- Change `closest("li")` to `closest("div")`. Reload, click Delete. Nothing happens —
  there's no `<div>` ancestor anywhere in a row, so `li` is `null` every time, and the
  guard clause bails out before anything else runs. Put it back to `"li"`.
- In the checkbox branch, change `li.classList.toggle("done")` to
  `event.target.classList.toggle("done")`. Reload, tick a box. Now the *checkbox
  element itself* gets the class, not the row — and the CSS rule
  (`#list li.done span`) only reacts to the class on the `<li>`, so nothing visibly
  changes. This is exactly why `closest("li")` matters: you need to act on the row as
  a whole, not on whichever specific child happened to be clicked. Put it back.
