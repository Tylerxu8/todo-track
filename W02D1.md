## 3. Why not one listener per row — what and why (~15 min)

The obvious approach: when you build a row in the submit handler, also do
`checkbox.addEventListener("click", ...)` and
`del.addEventListener("click", ...)` right there.

It works, and it's a trap:

- Every new task adds two more listeners. A hundred tasks, two hundred listeners.
- The logic for "what does delete do" now lives inside the row-builder, tangled up
  with `createElement` calls.
- If you ever rebuild the list (you will, tomorrow), you have to carefully re-attach
  every listener.

The better approach: **one** `click` listener on `<ul id="list">`, which never gets
rebuilt. When any click happens inside it, the event **bubbles up** from whatever was
clicked to the `<ul>`, and your one listener inspects `event.target` to decide what to
do. This is called **event delegation**. Read `sidelines/events.md` section
"Bubbling and delegation" now if you haven't.

## 4. The delegated listener — type it, don't paste (~35 min)

Add this to `app.js`, below the submit handler:

```js
list.addEventListener("click", (event) => {
  const li = event.target.closest("li");
  if (!li) return;

  if (event.target.matches('input[type="checkbox"]')) {
    li.classList.toggle("done");
  }

  if (event.target.matches("button.delete")) {
    li.remove();
  }
});
```

Every line, so you own it:

- `list.addEventListener("click", ...)` — one listener, on the container.
- `event.target` — the *exact* element that was clicked: the checkbox, or the button,
  or the span, or the `<li>` itself.
- `event.target.closest("li")` — starting from what was clicked, walk **up** the tree
  to the nearest `<li>` (including `event.target` itself if it is one). Returns that
  `<li>`, or `null` if the click wasn't inside any `<li>`.
- `if (!li) return;` — clicked somewhere in the `<ul>` but not in a row (the gap
  between rows, say). Nothing to do.
- `event.target.matches('input[type="checkbox"]')` — "is the thing I clicked a
  checkbox?" `.matches(selector)` returns true/false.
- `li.classList.toggle("done")` — add the class `done` if it's absent, remove it if
  it's present. The CSS from Day 4 does the rest.
- `event.target.matches("button.delete")` — "is the thing I clicked the Delete
  button?" (a `<button>` with class `delete`).
- `li.remove()` — detach the whole `<li>` from the tree. The row disappears.

Save, reload, add a few tasks, try the checkbox and Delete.

## 6. Break it deliberately (~10 min)

- Remove `const li = event.target.closest("li");` and the `if (!li) return;`, and
  change the branches to use `event.target.closest("li")` inline — actually simpler:
  just change `closest("li")` to `closest("div")`. Reload, click Delete. Nothing
  happens — there's no `<div>` ancestor, so `li` is `null` every time. Put it back.
- In the checkbox branch, change `li.classList.toggle("done")` to
  `event.target.classList.toggle("done")`. Reload, tick a box. Now the *checkbox*
  gets the class, not the row, and the CSS (`#list li.done span`) never matches, so
  nothing visibly changes. This shows why `closest("li")` matters — you need to act on
  the row, not the clicked control. Put it back.
